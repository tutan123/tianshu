## 二、能力对照：为什么这样分工

我不想吹自己。客观对比如下。

### GPT-6 明显强于我的

- **视觉审美判断**：它能"看一眼截图，觉得这里丑，然后改到好看"。我能截图、能看出明显缺陷（比如我发现了前景建筑淡化后变成一大块半透明脏板），但"怎样才好看"的迭代它比我快。
- **Computer Use**：它能真的操作浏览器做交互式调试。
- **Blender 手工建模**：弧顶、木构、格栅这类需要审美反复调整的模型。
- **演出/镜头/分镜**：互动影游的演出节奏感。

### 我明显强于 GPT-6 的（本轮已实证，不是承诺）

- **没有额度限制，能长时间连续跑**。我可以后台跑 10 分钟的浏览器回归、批量处理 2400 个文件。
- **真实浏览器自动化 + 截图**：本轮我已经在本机 Chrome 上跑了完整探针，产出 8 张截图 + JSON 报告。证据在 [`证据/`](证据/)。这一点你以为只有 GPT-6 能做 —— 其实我也能做，只是我截图后靠"代码 + 数值 + 结构"判断，它靠"眼力"判断。
- **跨文件逻辑审计**：我能通读全部模块，追踪 `flag → 存档 → 结局` 的整条链路。本轮我找到了一个 **GPT-6 和它的测试都没抓到的真实软锁**：实验楼小游戏失败会永久锁死一个结局（详见体检报告 B-1）。这种 bug 靠看截图永远发现不了。
- **可复现的验证基建**：单测、验收脚本、一键 `verify`、CI、基线快照。
- **批量文本 / 文档 / 素材许可台账 / 本地化**。
- **脚本化 3D 管线**：我本会话有 Blender MCP 可调用。`docs/build-clocktower.py`、`docs/export-kenney.py` 这类"跑脚本批量转 GLB、批量导出、检查合批"的活我可以做 —— 这不是审美活，是管线活。
- **终端 / 构建 / 数据 / 体积优化**。

### 结论

> **GPT-6 造东西，我保证东西没坏、并且说清楚坏在哪。**

## 四、协作回路（关键）

这个回路是整个分工能不能成立的唯一关键。**没有它，两个人写同一个仓库必然互相踩。**

```
① 用户把任务交给我（GPT-6 额度耗尽时）
       ↓
② 我读 03-项目速览 + 02-任务池，认领任务
       ↓
③ 我改代码 → 立刻跑 `verify.cmd`（单测 + 4 套浏览器验收 + 截图）
       ↓
④ 我产出「交接单」：改了哪些文件 / 验了什么 / 还剩什么没验
       ↓
⑤ GPT-6 额度恢复，读我的交接单接手，不重复劳动
       ↓
⑥ GPT-6 交活 → 我跑 verify → 出报告 → 回到 ③
```

### 硬性约定

1. **一个时间只允许一个 Agent 写代码。** 谁写谁先 `git add -A && git commit`。绝对不要两边同时改同一个文件。
2. **每次改动必须能通过 `verify.cmd`**。跑不过就不算做完。
3. **交活必须附交接单**（模板见 [`02-任务池与验收标准.md`](02-任务池与验收标准.md) 末尾）。
4. **禁止无理由重构架构**。原因见 [`03-项目速览-给下一个Agent.md`](03-项目速览-给下一个Agent.md) 的「不要动的东西」。
5. **改数值/加装备前必须同步改存档校验**，否则老存档会集体失效（体检报告 B-13）。
